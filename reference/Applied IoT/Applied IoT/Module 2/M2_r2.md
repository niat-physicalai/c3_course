# Part 1 — Giving an Input a Known State

## When an Input Cannot Be Trusted

Let us begin by being precise about what "reliable" means. A digital input is **reliable** when two things are true:

1. **The same physical situation always gives the same reading.** A released button reads HIGH every time, whatever else is happening nearby.
2. **The reading changes only when the physical situation truly changes.** No flicker, no phantom presses, no extra transitions.

An input can fail either test. Here are some symptoms you may recognise, and the family of causes behind each:

| What you see | What is going on |
|---|---|
| The reading flickers between HIGH and LOW when nothing is touching the button | The input has no defined state (a **floating input**) |
| One press is counted two or three times | The signal is not clean while the contacts settle (**bounce**) |
| The LED does the opposite of what you intended | The meaning of HIGH and LOW was misread (**active-low** confusion) |
| A sensor reads "detected" for the first minute after it is switched on | The sensor needs time to start up (a sensor characteristic) |
| The reading depends on whether you are touching the board | Electrical noise is reaching an undefined input |

These are different problems with different cures. The first family, inputs with no defined state, is the most fundamental, so we start there.

## Floating Inputs

### What "Floating" Means

Recall how an input pin works. It measures the voltage on its wire, and reports HIGH or LOW by comparing that voltage to two thresholds. Espressif's datasheet gives the input current of a pin as at most 50 nanoamperes. It is an extremely sensitive voltmeter that hardly draws any current from what it measures.

Now think about what happens when nothing is connected to the pin, or when it is connected only to something that is not currently connecting it to anything, such as a released button. The pin is **floating**: it is connected to no voltage at all.

A floating pin does not read "nothing". It has an electrical voltage that is *not being controlled by anything*. Because the pin draws almost no current, even the smallest stray charge can move its voltage. Sources of these include:

- electrical noise from nearby wires and components,
- the hum radiated by mains wiring,
- your own body, which acts as a small antenna and carries stray charge,
- the residual charge from a previous state.

The pin's voltage drifts around, and can sit anywhere, including the **undefined zone** between the LOW and HIGH thresholds you saw earlier. The reading may flicker between `True` and `False` from one moment to the next. The program is doing exactly what it should: it reads a voltage that means nothing.

```text
Button released, no pull resistor:

   input pin ──────┬──────  (nothing driving it)
                   │
                [ Button ]     open: no connection
                   │
                  GND

   The pin's voltage is undefined. It may read HIGH, LOW, or flicker.
```

> **Teaching model.** Think of a floating pin as a microphone with nobody speaking into it. It does not report silence. It picks up whatever is in the air.

### Observing a Floating Input

Let us see it happen. This program counts how many times the pin's reading changes in five seconds, with nothing driving the pin:

```python
import time
import board
import digitalio

pin = digitalio.DigitalInOut(board.CHOSEN_BUTTON_PIN)
pin.direction = digitalio.Direction.INPUT
pin.pull = None                      # no pull resistor: the pin is floating

changes = 0
last = pin.value
start = time.monotonic()

while time.monotonic() - start < 5:
    now = pin.value
    if now != last:
        changes += 1
        last = now

print("Changes in 5 seconds:", changes)
```

The program reads the pin as fast as it can for five seconds. Each time the reading differs from the previous one, it adds one to `changes`. It uses `time.monotonic()`, a clock that counts seconds since the board started, to know when five seconds have passed.

> **Try it: Observe an undefined input.** Wire the input pin to a button with the other side to ground, as before, but **do not press the button**.
> 1. **Predict.** With no pull resistor and the button released, how many changes do you expect in five seconds? Is the answer "none" because nothing is happening?
> 2. **Run** the program and read the count. Run it several times.
> 3. **Touch** the pin (or the wire connected to it) with a finger, or bring your hand near it, and run it again. Does the count change?
> 4. **Explain.** What does the result tell you about a pin that nothing is driving?
>

## Pull-Up and Pull-Down Resistors

### A Default Voltage

The cure for a floating input is to give the pin a **default voltage**, which is a voltage that applies whenever nothing else is driving it. You do this with a resistor connected from the pin to a power rail. Such a resistor is called a **pull resistor**, and there are two kinds:

- A **pull-up resistor** connects the pin to the **supply voltage** (3.3 V). By default, the pin reads **HIGH**.
- A **pull-down resistor** connects the pin to **ground**. By default, the pin reads **LOW**.

```text
        Pull-up                                  Pull-down

         3.3 V                                     3.3 V
           │                                         │
      [ R_pull ]                                 [ Button ]
           │                                         │
           ├────────► input pin                      ├────────► input pin
           │                                         │
      [ Button ]                                [ R_pull ]
           │                                         │
          GND                                       GND

  Released: pin = HIGH                      Released: pin = LOW
  Pressed:  pin = LOW                       Pressed:  pin = HIGH
```

### How a Pressed Button Overpowers the Pull Resistor

You may wonder: with a pull-up resistor connected to 3.3 V, how can pressing the button pull the pin all the way to 0 V? The answer is one you already know. It is a **voltage divider**.

When the button is pressed, the pull-up resistor and the button form a series circuit between 3.3 V and ground, and the pin sits at the junction:

```text
V_pin = 3.3 V × R_button ÷ (R_pull + R_button)
```

> **Example values.** A pressed button has a very small resistance, perhaps a fraction of an ohm to a few ohms. With R_pull = 45 kΩ (the typical internal value from Espressif's datasheet) and R_button = 1 Ω:
> V_pin = 3.3 × 1 ÷ 45,001 ≈ **0.00007 V**, effectively 0 V.

The pull resistor is called *weak* because it is large compared with what the button offers. It is strong enough to hold the pin at the supply voltage when the pin is otherwise unconnected, and weak enough to be completely overpowered when something else, such as a button, connects the pin to ground.

When the button is released, no current flows through the pull-up resistor at all (the input draws about 50 nA, which is negligible), so there is almost no voltage drop across it and the pin sits at essentially 3.3 V.

### Choosing Between Pull-Up and Pull-Down

Both work. Which you choose depends on the circuit:

| | Pull-up | Pull-down |
|---|---|---|
| **Default state** | HIGH | LOW |
| **Button wired between the pin and** | Ground | 3.3 V |
| **Pressed reads** | LOW (active-low) | HIGH (active-high) |
| **Common in** | Buttons and switches (the most common choice) | Signals that should be "off" by default |

Pull-ups are widely used with buttons because a button wired to ground is convenient, and the internal pull resistors are available for it. Whichever you choose, be clear about it, because it decides how you interpret the value.

### Internal or External?

You met the internal pull resistors in the previous reading. You can enable one in a single line:

```python
button.pull = digitalio.Pull.UP        # or digitalio.Pull.DOWN
```

Espressif's datasheet lists the ESP32-S3's internal weak pull-up and pull-down resistors at a typical value of about 45 kΩ. Internal pulls are convenient: no extra parts, no extra wiring. Sometimes, though, you add an **external** pull resistor instead of, or as well as, the internal one:

| | Internal pull | External pull |
|---|---|---|
| **Extra parts** | None | One resistor per input |
| **Typical strength** | Weak (about 45 kΩ) | Your choice (for example a few kΩ to 10 kΩ) |
| **Good for** | Simple buttons and short wires | Longer wires, noisy surroundings, or when a device requires it |
| **Watch out for** | May be too weak in noisy environments; a few pins have special start-up roles | More current flows when the input is pulled the other way |

The current trade-off is one you can calculate. When a pull-up input is pulled to ground:

- with the internal ~45 kΩ pull-up: 3.3 V ÷ 45 kΩ ≈ **73 µA**,
- with an external 4.7 kΩ pull-up: 3.3 V ÷ 4.7 kΩ ≈ **0.70 mA**.

A stronger (smaller) resistor holds the pin more firmly against noise, at the cost of more current whenever the input is pulled the other way. For a battery-powered device, that difference matters. For a button, it is a design decision, not a right-or-wrong choice.

A few further points:

- Some modules and sensor boards **already include** a pull resistor on their output. Read the documentation before adding another. (If an external pull is already present, enabling an internal one is not harmful. It simply uses slightly more current.)
- Some pins, including the strapping pins Espressif documents for the ESP32-S3, have special roles at start-up. A pin choice that is fine in a program can still interfere with how the chip starts, so stick with the plain general-purpose pins for your inputs.

> **Try it: Compare with and without a pull.** Return to the floating-input program from before.
> 1. Change `pin.pull = None` to `pin.pull = digitalio.Pull.UP`.
> 2. Run it again with the button released, then touch the pin or bring your hand near it. How does the count of changes compare with the floating case?
> 3. Measure the voltage on the pin with a multimeter, with the button released and pressed.
> 4. **Explain.** What has the pull-up changed about the pin's voltage, and about the program's readings?

### The Rule for Input Reliability

We can now state a rule that will serve you for every input you ever connect:

> **Every digital input must have a defined state at all times.** That state comes either from a pull resistor, or from a device that actively drives the line to both HIGH and LOW.

A button connects the pin to only one level (ground) and leaves it open the rest of the time, so it needs a pull resistor. Some sensor modules actively drive their output to both levels, and need none. Some only pull their output LOW and leave it unconnected otherwise, so they need a pull-up. You will meet this last case among the sensors, later in this reading.

# Part 2 — Mechanical Buttons: Bounce and Debouncing

## Button Bounce

Now the button has a defined default state, but a second source of unreliability remains, and it is built into the way mechanical switches work.

### What Happens During a Press

Inside a push button, a metal contact moves to touch another. Metal is springy and the motion is fast. When the two surfaces meet, they do not simply stay together. They **rebound**, break contact, meet again and settle, much like a ball dropped on a table bounces a few times before it rests. Each brief contact and break is a real electrical transition, so the signal from a single physical press may look like this:

```text
Ideal press:                       What can actually happen:

  HIGH ─────┐                        HIGH ─────┐ ┌┐ ┌─┐
            │                                  │ ││ │ │
  LOW       └──────────                  LOW   └─┘└─┘ └───────────
        (press)                            (press)   ↑ bounce ↑
                                                (a few milliseconds)
```

This is **contact bounce**. It also happens when the button is *released*.

How long does it last? People have measured it. In a well-known study, embedded systems engineer Jack Ganssle tested 18 kinds of switches, pressing each many times. After setting aside two outliers, the remaining switches showed an average bounce of about 1.6 milliseconds and a longest bounce of about 6.2 milliseconds. He found that most switches bounce for less than 10 ms.

Those times seem tiny. But think about the speed of your program. Even a simple CircuitPython loop can check the pin hundreds or thousands of times per second. To such a loop, 2 milliseconds is not brief at all. It is long enough to read the pin several times, seeing HIGH, LOW, HIGH, LOW before it settles.

### What Bounce Does to a Program

Whether bounce matters depends on *what your program does with the input*.

- **Reading the level.** In the previous reading, the first button → LED program simply copied the button's state to the LED. A few milliseconds of flicker on the LED are invisible to your eyes, so bounce goes unnoticed.
- **Detecting an event.** The toggle program and the press counter reacted to the *moment of change*. Each bounce looks like a new press, so a single press can toggle the LED two or three times, or be counted several times, depending on where the bounces fall.

```text
One physical press, read as raw samples:   H H H L H L L L L L L L
Falling edges (H → L) the program sees:        ↑ ↑                     = 2 "presses"
```

The bug is not in your program's logic. The logic correctly says "count every time the input goes LOW", and the input really did go LOW twice. The *signal* was not trustworthy.

### Observing Bounce

You can look at the effect on your own button. This program counts every high-to-low transition, with no debouncing at all:

```python
import time
import board
import digitalio

button = digitalio.DigitalInOut(board.CHOSEN_BUTTON_PIN)
button.direction = digitalio.Direction.INPUT
button.pull = digitalio.Pull.UP

count = 0
last = button.value

while True:
    now = button.value
    if last and not now:             # a falling edge: HIGH to LOW
        count = count + 1
        print("Presses counted:", count)
    last = now
```

> **Try it: Count the presses.**
> 1. **Predict.** If you press the button exactly 20 times, what count do you expect? What could make it different?
> 2. **Test.** Press it 20 times, with deliberate, separate presses, and note the final count. Repeat with different pressing styles: gentle, hard, quick.
> 3. **Explain.** If the count is above 20, what caused the extras? If it is exactly 20, does that prove your button does not bounce? (Hint: think about how quickly the program samples the pin, and what different switches do.)

Some buttons bounce a lot, and others very little, so results vary from button to button. That is exactly why you should test your own instead of assuming.

### Seeing Bounce Without Hardware

If your button happens not to bounce noticeably, or you want to study the effect closely, you can **simulate** it. The program below feeds a made-up list of readings, the kind of sequence a bouncing button might produce, to a counter. It runs on your board or in any Python environment:

```python
# One physical press, sampled every millisecond.
# True = released (HIGH), False = pressed (LOW).
samples = [True]*5 + [False, True, False, True] + [False]*10 + [True, False, True] + [True]*5

count = 0
last = samples[0]
for value in samples[1:]:
    if last and not value:           # falling edge
        count = count + 1
    last = value

print("Presses counted:", count)
```

> **Try it: Predict before running.** Read the list carefully. There is one physical press and one release. How many falling edges do you count in the list by hand? Then run the program and compare. Now find the second cluster of transitions near the end. What physical event does it represent?

## Debouncing: Making One Press Look Like One Press

**Debouncing** means making sure that one physical action produces one clean transition in your program. The idea behind all debouncing is the same:

> **Do not believe a change until it has stayed changed for long enough.**

If the input goes LOW and then bounces back HIGH within a couple of milliseconds, it was not a real, lasting press. If it goes LOW and *stays* LOW for, say, 30 milliseconds, then the press is real.

### How Long Should You Wait?

The waiting time is a design decision with a trade-off:

- **Too short:** a slow-settling switch may still cause false triggers.
- **Too long:** the system feels sluggish, and quick, genuine taps may be missed.

Since most switches stop bouncing within about 10 ms, and a delay of around 50 ms feels instantaneous to a person, Ganssle suggests choosing a debounce period somewhere in the range of 20 to 50 ms. Values in that range are a sensible starting point. Then measure and adjust for your own button.

### Hardware Approaches

You can debounce with **hardware** instead of code, and you already know the ingredients. An RC circuit (a resistor and capacitor, as in the earlier reading) makes the voltage change gradually, which smooths out fast bounces. Because a slowly changing voltage can spend a while in the undefined zone between HIGH and LOW, such circuits are often followed by a special component (a **Schmitt trigger**) that turns a gradual transition into a sharp one. There are also dedicated debounce chips, and latch circuits for switches with two positions.

### Software Approaches

The alternative is to handle it in **code**. There are two approaches you will meet.

**Approach 1: Wait and check again (simple, but blocking).** When a change is detected, wait a short time, then check whether the input is still in the new state:

```python
if not button.value:             # it looks pressed
    time.sleep(0.02)             # wait 20 ms for the bounce to settle
    if not button.value:         # still pressed? then it is real
        print("Pressed")
```

This is easy to understand, and works for simple cases. Its drawback is that the program does *nothing else* during the wait. For 20 ms, that hardly matters. But if your program also has to blink an LED, watch a sensor or respond to something else, then waiting is wasteful, and the approach does not handle release bounce on its own.

**Approach 2: Require the input to stay changed (non-blocking).** Instead of stopping to wait, the program keeps running, and *keeps a timer*. It remembers when the raw reading last changed, and only accepts a new state once the reading has stayed the same for the debounce time:

```python
import time
import board
import digitalio

led = digitalio.DigitalInOut(board.CHOSEN_LED_PIN)
led.direction = digitalio.Direction.OUTPUT

button = digitalio.DigitalInOut(board.CHOSEN_BUTTON_PIN)
button.direction = digitalio.Direction.INPUT
button.pull = digitalio.Pull.UP

DEBOUNCE_TIME = 0.03                 # seconds the input must stay changed

stable_state = button.value          # the state we currently trust
last_reading = stable_state          # what we saw on the previous loop
last_change = time.monotonic()       # when the raw reading last changed

while True:
    reading = button.value
    now = time.monotonic()

    if reading != last_reading:      # the raw signal moved: restart the timer
        last_change = now
        last_reading = reading

    if reading != stable_state and (now - last_change) >= DEBOUNCE_TIME:
        stable_state = reading       # it has stayed put long enough: accept it

        if not stable_state:         # LOW means pressed (pull-up wiring)
            print("Pressed")
            led.value = not led.value
        else:
            print("Released")
```

This is the most important piece of code in this reading, so let us go through it slowly.

- **Two states are kept.** `last_reading` is the *raw* pin value on the previous loop. `stable_state` is the value the program has decided to *trust*.
- **Every time the raw reading changes, the timer restarts.** `last_change = now`. During bounce, the reading keeps changing, so the timer keeps restarting.
- **A new state is accepted only after the timer has run out.** When the reading differs from the trusted state *and* has been unchanged for `DEBOUNCE_TIME`, `stable_state` is updated. That is the moment your program finally "believes" the change, and that is where the action happens.
- **Nothing blocks.** The loop keeps running, so it could do other work each time round.

Here is the effect on one bouncing press, with a 30 ms debounce time:

```text
raw pin:       H H H L H L L L L L L L L L L L L L L L L L …
timer:         — — — ↺ ↺ ↺ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ✔
trusted state: H H H H H H H H H H H H H H H H H H H H H L
                                                      ↑ 30 ms after the last change
```

The bounces restart the timer (↺), so nothing is accepted until the signal has been steady for 30 ms. Then there is exactly **one** "Pressed".

The price is a small delay. The program acts about 30 ms after the physical press, but that is imperceptible to a person.

### Making It Reusable

Because sensors and switches beyond buttons need this too, it helps to wrap the logic in a small **class** that you can use for any digital input. It is the same method, tidied:

```python
import time

class StableInput:
    """Wraps a digital input and reports a debounced value."""

    def __init__(self, pin, settle_time=0.03):
        self.pin = pin                     # a digitalio.DigitalInOut input
        self.settle_time = settle_time     # seconds the input must stay changed
        self.stable = pin.value            # the state we trust
        self.changed = False               # True for one loop after a change is accepted
        self._last_raw = self.stable
        self._changed_at = time.monotonic()

    def update(self):
        raw = self.pin.value
        now = time.monotonic()
        self.changed = False

        if raw != self._last_raw:          # raw signal moved: restart the timer
            self._last_raw = raw
            self._changed_at = now

        if raw != self.stable and now - self._changed_at >= self.settle_time:
            self.stable = raw              # accept the new state
            self.changed = True

        return self.stable
```

Using it is short and readable:

```python
button_pin = digitalio.DigitalInOut(board.CHOSEN_BUTTON_PIN)
button_pin.direction = digitalio.Direction.INPUT
button_pin.pull = digitalio.Pull.UP

button = StableInput(button_pin)

while True:
    button.update()
    if button.changed and not button.stable:      # a clean press
        led.value = not led.value
```

The `update()` method must be called every time round the loop, and it does the timing for you. `changed` is `True` for exactly one loop, at the moment a new stable state is accepted, which is the "event" you learned to detect earlier, now free of bounce.

> **Assumption about timekeeping.** `time.monotonic()` counts seconds as a floating-point number, which is precise for a long time but gradually loses precision when a program has run for many hours or days. That does not matter for the experiments in this course. For very long-running devices, CircuitPython also provides `time.monotonic_ns()`, which counts in whole nanoseconds, and `supervisor.ticks_ms()`, a millisecond counter.

### Tools That Already Exist

You do not always have to write debouncing yourself. Two ready-made tools are worth knowing about:

- **The `keypad` module.** Many CircuitPython builds include a built-in `keypad` module for scanning buttons. Its scanners check keys at a set interval (20 ms by default) and report clean *pressed* and *released* events. Adafruit describes it as the preferred way to debounce.
- **The `adafruit_debouncer` library.** An add-on library that wraps a pin and provides properties such as `value` (the stable value), `fell` and `rose` (the moment it just changed).

Here is the `keypad` version of the button monitor:

```python
import board
import keypad

keys = keypad.Keys((board.CHOSEN_BUTTON_PIN,), value_when_pressed=False, pull=True)

while True:
    event = keys.events.get()        # None if nothing has happened
    if event:
        if event.pressed:
            print("Pressed")
        if event.released:
            print("Released")
```

`value_when_pressed=False` says that the pin reads LOW when the key is pressed, and `pull=True` enables the appropriate internal pull resistor (a pull-up in this case). Events accumulate in a queue, and `keys.events.get()` takes the next one.

> **Assumption.** The `keypad` module is not present in every CircuitPython build. Check that `import keypad` works in the REPL on your board before relying on it. External libraries such as `adafruit_debouncer` need to be copied to the board's `lib` folder, and you will work with libraries in later modules. The point of knowing what is *inside* these tools, the same idea of "stay changed for long enough", is that you can trust them, and fix things when they misbehave.

### Choosing an Approach

| Approach | How it works | Strengths | Trade-offs |
|---|---|---|---|
| **Hardware** (RC circuit, Schmitt trigger, debounce chip) | Cleans the signal before it reaches the pin | No code, works even if the program is busy | Extra parts, extra wiring, more to design and test |
| **Software: wait and re-check** | Pause briefly, then read again | Very simple to write | Blocks the program; handles only simple cases |
| **Software: stable-for-time** | Accept a change only after it stays for the debounce time | Non-blocking; handles press and release | A little more code |
| **Ready-made tools** (`keypad`, debouncer library) | Wrap the logic for you | Short, tested code | Depend on the library being available |

For most microcontroller projects, software is the natural first choice, because it costs nothing extra to build and is easy to change. Hardware debouncing earns its place when the signal must be clean before it reaches the chip, or when the microcontroller cannot spare the time.

## Stable Digital Input States

We can now say what it takes to have a digital input you can trust. There are three parts, and each answers one of the problems we met:

| Problem | Cure |
|---|---|
| The pin has no defined voltage (floating) | A pull-up or pull-down resistor, internal or external |
| The signal is not clean while a contact settles (bounce) | Debouncing, in hardware or software |
| The reading is misinterpreted (active-low confusion) | Name the state by its meaning, and test each physical state |

A short **checklist** for any digital input:

- Does it have a defined default state, from a pull resistor or from a device that drives both levels?
- Is the pull direction the one you intended (pull-up for a button to ground)?
- Do you know what HIGH and LOW *mean* for this input?
- If the program reacts to changes, is the input debounced?
- Do the voltage levels match the 3.3 V input?
- Is the ground shared, and are the wires short and firmly connected?

## Diagnosing an Unreliable Input

When an input misbehaves, avoid guessing. Use the habit you have been building, and a method for systematic fault-finding:

```text
Observe → Isolate → Measure → Hypothesize → Test → Fix → Verify
```

- **Observe** exactly what happens, and when. Does it happen with no one touching anything? Only during presses? Every time or occasionally?
- **Isolate** which link of the chain is misbehaving: the physical device, the wiring, the pin's voltage, the program's reading or the program's logic.
- **Measure** the pin's voltage with a multimeter, and print raw readings.
- **Hypothesize** a cause, **test** it with one change, **fix** it and **verify** that the problem is gone.

| Symptom | Likely cause | First thing to check |
|---|---|---|
| Random readings with nothing touching | Floating input | Is a pull resistor enabled or connected? |
| Readings change when a hand approaches | Floating or very weakly pulled input | Pull resistor, wire length |
| One press counts two or more times | Bounce | Is the input debounced? Print the raw transitions |
| Quick taps are missed | Debounce time too long, or the loop is slow or blocked | Debounce time; anything blocking the loop (long sleeps) |
| Input always reads the same, whatever you do | Wrong pin, wiring fault or pin already in use | Pin name, wiring, measure the pin |
| Logic is the opposite of what you expect | Active-low input read as active-high | Pull direction and how the value is interpreted |
| Works when you press hard or wiggle the wire | Loose connection | Reseat the wires and the button |

A helpful diagnostic tool is a program that prints **every raw transition with a timestamp**, so you can *see* what the input is really doing:

```python
import time
import board
import digitalio

button = digitalio.DigitalInOut(board.CHOSEN_BUTTON_PIN)
button.direction = digitalio.Direction.INPUT
button.pull = digitalio.Pull.UP

last = button.value
start = time.monotonic()

while True:
    now = button.value
    if now != last:
        elapsed_ms = int((time.monotonic() - start) * 1000)
        print(elapsed_ms, "ms:", "HIGH" if now else "LOW")
        last = now
```

Run it and press the button. If several transitions appear within a few milliseconds, you are watching bounce directly. If a long quiet gap follows, and then a cluster, you are seeing the press and the release. If transitions appear with no one touching the button, you are watching a floating or noisy input.

> **Note.** How much bounce you see depends on your button and on how fast your loop runs. If you do not see any, the simulation earlier in this reading still illustrates the effect.

# Part 3 — Digital Sensors

## From Buttons to Digital Sensors

A button lets a *person* give the system information. A **digital sensor** lets the *physical world* do it. Both present a two-state signal to a pin, and everything you have learned about reliable inputs applies to both.

For this reading, a **digital sensor** is a device that detects a condition in the physical world and reports the result as a **HIGH or LOW signal** on an output pin. The reported condition is a yes-or-no question: *Is there motion? Is the door open? Is the object close?*

### How a Digital Sensor Differs from a Button

A bare button only opens or closes a path. It contains no electronics, and you provide the power and the pull resistor yourself. Many digital sensors come as **modules**: a small board that packages a detector together with some circuitry. That circuitry typically:

- turns the detector's raw response into a clean HIGH or LOW,
- may include a **threshold**, so the output flips only when the condition passes a certain level (some modules have a small adjustable knob to set it),
- and needs its **own power** and a ground connection.

```text
Physical condition ──► [ detector ] ──► [ sensor circuitry ] ──► OUT pin ──► ESP32-S3 input pin
                                              ▲
                                     power (VCC) and GND
```

So a digital sensor module usually has three connections: **power**, **ground** and **output**. Your job is to connect the output to a GPIO input, power the module correctly and read the pin.

> **Teaching model.** Two other kinds of sensors exist, and are *not* the subject of this reading. **Analog sensors** produce a voltage that varies smoothly, and **data sensors** send measured numbers over a communication interface. Both are covered in later readings. A digital sensor, as we use the term here, gives just two states.

### Some Common Digital Sensors

> **Assumption.** These are common types of digital-output modules. Your course kit may include some of them, or others. Use the one in your kit, and always check its own documentation.

| Physical condition | Typical sensor | What HIGH or LOW usually indicates |
|---|---|---|
| Motion of a warm body | PIR (passive infrared) motion module | Motion detected, or not |
| Door or window open or closed | Magnetic reed switch and magnet | Magnet near, or not |
| Tilt or vibration | Tilt switch | Tilted, or not |
| Nearby object | Infrared obstacle-detection module | Object present, or not |
| Something touching a pad | Touch sensor module | Touched, or not |
| A mechanical limit reached | Limit switch | Pressed, or not |

The meaning of HIGH and LOW differs from module to module. That is not a defect. It is the *active-high or active-low* idea again, and the documentation or a quick test tells you which one you have.

## Reading a Sensor's Documentation Before Wiring

Before you connect any sensor module, find out five things from its documentation. This takes a couple of minutes and can prevent damaged parts and hours of confusion.

1. **Supply voltage.** What voltage does it need on its power pin: 3.3 V, 5 V or either?
2. **Output voltage level.** When the output is HIGH, what voltage does it produce? This may differ from the supply voltage.
3. **Output type.** Does the output actively drive both HIGH and LOW, or does it only pull LOW (and need a pull-up)?
4. **Active level.** Is the output HIGH or LOW when the condition is detected? What does it read when idle?
5. **Timing behaviour.** Is there a start-up (warm-up) period? Does the output stay active for a minimum time after a detection?

Two of these deserve a closer look.

### Voltage Compatibility

Your ESP32-S3's input pins are designed for **3.3 V signals**. Espressif's datasheet gives the highest input-high voltage for its pins as the supply voltage plus 0.3 V, which is about 3.6 V when the chip is running at 3.3 V. A 5 V signal is outside that specification and can damage the pin.

This creates a rule with several solutions:

- **Power the module from 3.3 V**, if its documentation says it works at that voltage. The output is then at most 3.3 V.
- Check whether the module **powers at 5 V but outputs 3.3 V**, which many do. Its documentation will say.
- If a 5 V output is unavoidable, use a **level-shifting** circuit designed for the purpose. For a slow signal, a simple **voltage divider** (which you know from the first module) can also reduce a 5 V signal to a safe level.

> **Example values.** A divider of 10 kΩ (upper) and 20 kΩ (lower) turns 5 V into 5 × 20 ÷ (10 + 20) ≈ 3.3 V. This is an illustration of the principle. Whether it suits a particular sensor depends on that sensor's output and how fast the signal changes, so check the documentation or ask before building one.

### Output Type: Actively Driven or Open

Recall the rule for input reliability: every input must have a defined state. A sensor module's output might satisfy that in either of two ways:

- **It actively drives both levels.** Its output circuit connects the pin to the supply for HIGH and to ground for LOW. The pin always has a defined voltage, and needs no pull resistor. This kind of output is often called **push-pull**.
- **It only pulls LOW.** Its output connects the pin to ground when active, and leaves it *floating* otherwise. Such an output (often called **open-drain** or **open-collector**) needs a **pull-up resistor** to give it a HIGH state. Some modules include one, and others do not.

If a sensor's output floats when it is inactive, you already know what will happen: unreliable, flickering readings. The cure is one you also already know.

## Connecting and Reading a Digital Sensor

### Wiring

Follow the same careful order as before:

1. **Disconnect USB** so the board is unpowered while you wire.
2. **Connect the sensor's power pin** to the supply pin specified in its documentation (3.3 V or 5 V).
3. **Connect the sensor's ground pin** to a GND pin on the board. The sensor and the board must share a ground.
4. **Connect the sensor's output pin** to the GPIO pin you chose for an input.
5. **Check the wiring** against the documentation before reconnecting USB.

### Characterise Before You Build

Before writing any decision logic, find out what the sensor actually does. This short program prints the raw value, so you can see the sensor's two states:

```python
import time
import board
import digitalio

sensor = digitalio.DigitalInOut(board.CHOSEN_SENSOR_PIN)
sensor.direction = digitalio.Direction.INPUT
# sensor.pull = digitalio.Pull.UP   # enable only if the documentation says the output needs a pull-up

while True:
    print(sensor.value)
    time.sleep(0.2)
```

> **Try it: Predict, measure, explain.**
> 1. **Predict.** Based on the documentation, what should the pin read when the sensor is idle? When it detects something?
> 2. **Run** the program, and trigger the sensor: wave a hand, bring a magnet close, tilt it, or whatever your sensor responds to.
> 3. **Observe.** Which value means "detected"? Does the value change instantly? How long does it stay in the detected state? Does anything unexpected happen right after power-up?
> 4. **Measure.** Use a multimeter to measure the voltage on the output pin in each state. Are the levels what the documentation said?
> 5. **Explain.** Does everything match? If not, what does the difference tell you?

Some sensor types have particular habits, which is why characterising them first is worthwhile. For example, motion modules based on PIR sensors are commonly documented as needing a start-up period of up to about a minute after power is applied, during which their output may behave erratically, and often have a setting that decides how long the output stays HIGH after motion is detected. Confirm what applies to *your* module.

### Interpreting the Sensor's State

Once you know which value means "detected", give it a meaningful name once, near the top of your program, and use that name in the rest of the logic. This keeps active-high and active-low details in one place:

```python
DETECTED_LEVEL = True      # set this from your own test: True if the output is HIGH when detecting

def detected():
    return sensor.value == DETECTED_LEVEL
```

Now the rest of your program reads like the physical situation: `if detected():`. If you swap in a sensor with the opposite polarity, you change one line.

## Using a Sensor's State in Program Logic

Now we come to the payoff: making the program respond. As with the button, there are two kinds of logic.

### Following the Sensor

The simplest response mirrors the sensor: the output is on while the sensor detects something.

```python
while True:
    if detected():
        led.value = True
    else:
        led.value = False
    time.sleep(0.05)
```

Here is the whole chain, matching the model you know:

```text
Sense:    the sensor detects a condition in the physical world
Compute:  the program reads the pin, interprets it and decides
Actuate:  the program sets an output: LED, buzzer, or another digital actuator
```

### Reacting to a Change, and Holding the Response

Often you do not want the response to follow the sensor exactly. A motion sensor may report motion in bursts, and a light that flickers on and off with every burst would be irritating. A better response is to **react to detection, then hold** the output on for a set time after the *last* detection.

```python
import time
import board
import digitalio

HOLD_TIME = 5                    # seconds to keep the light on after the last detection

led = digitalio.DigitalInOut(board.CHOSEN_LED_PIN)
led.direction = digitalio.Direction.OUTPUT

sensor = digitalio.DigitalInOut(board.CHOSEN_SENSOR_PIN)
sensor.direction = digitalio.Direction.INPUT

DETECTED_LEVEL = True            # set from your own test

led_off_at = 0                   # the time at which the LED should turn off

while True:
    if sensor.value == DETECTED_LEVEL:
        led.value = True
        led_off_at = time.monotonic() + HOLD_TIME     # restart the countdown
    elif time.monotonic() > led_off_at:
        led.value = False

    time.sleep(0.05)
```

Read it as a story. Every time the sensor detects something, the LED is turned on and a "turn off at" time is set five seconds into the future. If detections keep coming, the time keeps moving forward, and the LED stays on. Once detections stop and the time is reached, the LED turns off. The program never stops to wait: it keeps checking the sensor while the countdown runs. The variable `led_off_at` is the program's *memory* of when it last saw something.

You can also react to a **change in the sensor's state**, exactly as you did with the button, for example "the moment motion is first detected":

```python
was_detected = False

while True:
    now_detected = detected()

    if now_detected and not was_detected:
        print("Detected!")               # runs once per detection

    if was_detected and not now_detected:
        print("Cleared")                 # runs once when the detection ends

    was_detected = now_detected
    time.sleep(0.05)
```

### Sensors Need Reliable Input Too

Everything in this reading applies to sensors, because a sensor's output is a digital input:

- **Mechanical sensors bounce.** A reed switch, a tilt switch and a limit switch all have mechanical contacts, and they bounce just like a button. If your program reacts to *changes*, debounce them. The `StableInput` class from earlier works unchanged: wrap the sensor's pin in it, call `update()` every loop and use `changed` and `stable`.
- **Electronic sensors can chatter near a threshold.** A sensor module that compares a physical quantity with a threshold may flip repeatedly when the quantity hovers near that threshold. The same "stay changed for long enough" idea can steady it. Some modules also have built-in delays that do a similar job.
- **A floating output is still floating.** If a sensor's output can float when idle, it needs a pull-up.
- **Wiring faults look like unreliable sensors.** A loose power or ground wire produces intermittent, strange behaviour. Check wiring before blaming the sensor.

To see how the pieces combine, here is the "detect, then hold" program using a debounced sensor. The `StableInput` class from earlier is assumed to be defined above it:

```python
sensor_pin = digitalio.DigitalInOut(board.CHOSEN_SENSOR_PIN)
sensor_pin.direction = digitalio.Direction.INPUT

sensor = StableInput(sensor_pin, settle_time=0.05)
DETECTED_LEVEL = True

led_off_at = 0

while True:
    sensor.update()

    if sensor.stable == DETECTED_LEVEL:
        led.value = True
        led_off_at = time.monotonic() + HOLD_TIME
    elif time.monotonic() > led_off_at:
        led.value = False
```

# Putting It All Together

## The Complete Path, Now with Trustworthy Signals

Here is the flow you established in the previous reading, with the reliability layer we have added:

```text
Physical condition
      │
      ▼
Sensor or button                      ← has a defined idle state; contacts may bounce
      │
      ▼
Clean, stable digital signal          ← pull resistor + debouncing (or a stable sensor output)
      │
      ▼
GPIO input on the ESP32-S3            ← 3.3 V levels only
      │
      ▼
Program: interpret → decide           ← meaningful names, event logic, timers
      │
      ▼
GPIO output → actuator                ← LED, buzzer or another digital actuator
      │
      ▼
Physical action
```

The insight of this reading is in the second and third boxes. **Reading a pin is easy. Trusting the reading takes some engineering.**
